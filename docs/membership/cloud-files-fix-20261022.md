# 云空间显示与上传中断修复

## 已确认原因

1. 书源同步内容在 PostgreSQL 的 `sync_entities` 中。云空间页面另外提供了 SOURCE JSON 文件的上传入口，与正常同步重复。
2. 云空间 `meter` Builder 将初始的 0 字节和空重置日期按值传入。编译后的更新回调捕获旧参数，没有读取 `@State summary`，因此后台返回新数据后页面仍显示 0。
3. 用户提供的生产日志显示：65MB EPUB 的分块 0—58 已成功；15:07:30 的下一次 `upload-ticket` 触发全局 `RATE_LIMITED`，重试和摘要请求也被限流。插件抛出的普通对象被统一错误处理器误转成 HTTP 500。客户端只立即重试一次，无法等待剩余的 3 秒窗口。用户随后手工继续上传成功，确认分块持久化正常。

## 修改

- 云空间只提供书籍与字体的上传、下载；书源仍走数据同步。服务端拒绝新增 SOURCE 文件，未删除历史文件或数据库记录。书源在 PostgreSQL 中的占用仍计入已确认的共用空间规则。
- 容量、下载用量和重置日期直接读取响应式状态；首次未获取时显示“暂未获取”。摘要请求失败不再阻止读取本地未完成上传任务，刷新也不会覆盖原上传错误。
- 全局限流返回已有的 `AccountRateLimitError`，统一处理为 HTTP 429，正文 `retryAfter` 与响应头为数字秒数。保留现有请求上限。
- 上传准备、清单、授权、确认、完成，以及下载授权均对暂时失败做有限重试。429 按服务端秒数等待，页面显示倒计时；暂停或换账号能中断等待。重试保持原请求体及下载 requestId，避免重复计量。

## 验证

- 服务端 `npm test`：82 项通过，包含真实 Fastify 限流插件与生产注册/错误处理代码的回归，确认返回 429 而非 500。
- 客户端云传输、自动同步、字体导入检查：11 项通过。模拟 65 个 1MiB 分块穿过 120 次请求窗口、等待后完成、下载授权重试不换计费标识、暂停和账号切换中断。

- `assembleHap` 成功；未做设备与真实网络的端到端复验。

## 部署

客户端使用本次 `entry-default-signed.hap`。服务端上传 `qingye-cloud-files-fix-20261022.zip` 到 `/root`，执行：

```bash
stage=$(mktemp -d /root/qingye-cloud-files-fix.XXXXXX)
unzip -q /root/qingye-cloud-files-fix-20261022.zip -d "$stage"
bash "$stage/deploy-cloud-files-20261022.sh"
```

脚本核验 SHA256、基线代码匹配、工作目录和语法，备份现有两个运行模块，仅替换限流回调和新增 SOURCE 上传拒绝逻辑；未知基线拒绝修改。重启后检查本机及 HTTPS 健康状态，失败时恢复备份。不会执行数据库迁移、修改配置或清理上传任务。限流误报的完整修复需要服务端补丁与新版客户端配合。

本轮仅生成部署包，未在生产服务器执行。安装与部署后可用同一 EPUB 验证自动等待续传，并检查存储用量包含现有字体、书籍和上传预留空间。
